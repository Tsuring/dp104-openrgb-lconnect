# Implementation and evidence boundaries

## Target and delivery state

The original inputs are **DP104 master 1.2.0 8K** and PLC 1.2.0, pinned in [the target manifest](../firmware/targets/dp104-v1.2.0-8k.json). That manifest identifies the stock inputs, not the generated installed images. The ordinary master has different addresses and is not interchangeable. A version reply alone does not identify the running polling-rate variant.

Compatibility application **1.2.1** is installed on both master and PLC, built from those 1.2.0 inputs. Normal E104 enumeration, VIA 12, fresh application queries, real CAPS readiness and complete 104-output COMMIT acknowledgements were observed. The real DP104 appears at raw SDK index 6 and L-Connect ID 6 in the tested topology. The accepted master includes F4/F6 diagnostics and the tail-preserving FIFO receive correction; the accepted PLC includes F5 diagnostics and circular 128-byte receive draining. Both corrections are described below. Temporary native diagnostics were removed after the bounded acceptance run, restoring the original OpenRGB executable and all thirteen lighting profiles. The 8.8-inch screen project remains separate.

Flash readback, real 8K timing, maximum heap/stack demand and independent recovery of a corrupted PLC remain unverified.

## Data path

The native OpenRGB controller accepts 104 colors and sends BEGIN, thirteen DATA reports and COMMIT through the existing HID interface. Every response is checked. The master forwards only actual matching PLC responses; a successful COMMIT means the PLC accepted and published the complete CRC-checked frame. USB submission failure retains the reply for retry unless a newer request supersedes it.

The internal UART uses fixed 46-byte D2 envelopes and bounded stream reassembly across fragmented or coalesced receive callbacks. The old escaped envelope is incompatible and is dropped as a complete reserved record. Legacy records remain opaque. The PLC IRQ drain copies newly received spans into a bounded FIFO; task context parses requests, handles leases and transmits acknowledgements. See [the protocol](protocol.md).

The PLC receiver stages complete frames, publishes atomically to the existing 104-output buffer and gates the stock setter during direct ownership. Scanning, display and the existing serializer remain in their original main loop. A 1000 ms lease releases ownership to the stock renderer. The fixed-wire physical regressions included a 60-second fast varied run of 1,223 frames and 19,624 exact exchanges, no retries or foreign reports, a 16 ms maximum observed reply, and natural lease expiry without RELEASE. Slow zero-heavy and bare-marker regressions each completed 248 frames. These firmware regressions do not validate the later-added native worker recovery. The user confirmed continued operation of the spatially corrected Wave and changes to color, brightness, speed and left/right direction.

## Native transport recovery and status

The native worker coalesces updates in a latest-frame mailbox. After a transport failure, it waits using an interruptible 250 ms backoff, establishes a fresh protocol session with a real CAPS exchange, then sends only the newest queued frame with a new transaction. It does not replay the failed request or transaction. Recovery permits at most three unsuccessful attempts during the 10-second window that starts with the initial failure. A persistent fault moves the worker to a terminal state instead of retrying indefinitely; without a successful COMMIT, the PLC's existing one-second lease returns output to its built-in renderer.

Native source exports `g_dp104RuntimeStatus`, a data-only 144-byte schema-1 diagnostic block with atomic 32-bit fields. It records exchange and frame counters, first and latest failure details, recovery counters/state and protocol readiness. A reader can inspect the block without hooks, injection or HID requests. The block assumes one active DP104 controller; duplicate candidate lifecycles can temporarily affect its global readiness field. The installed build was observed with 180 one-second samples using read-only process-memory access and no hooks, injection or device commands: completed frames increased from 39 to 4,326, with 64,897 total exchanges and zero exchange/frame failures. Recovery was not needed in that run; its fault paths passed mock tests for CAPS failure, latest-frame replacement during CAPS, three-attempt exhaustion, ten-second expiry and shutdown during backoff.

## Host deadline handling and optional diagnostics

The native transport source continues reading when a zero-byte HID read returns before the existing 100 ms deadline. It neither resends the request nor extends that deadline, and rejects replies at or after the deadline. A regression queues a matching acknowledgement after an early zero read. This correction is test-verified and a normal candidate was built, but it is not installed; the accepted firmware run does not establish hardware acceptance of that separate native candidate.

`DP104_CAPTURE_FAILURE_DIAGNOSTICS` is disabled by default. Enabling it adds one-shot failure evidence collection after a failed exchange; diagnostic requests can replace the pending bridge slot and are intended for controlled investigation. Normal builds retain passive runtime counters without those active diagnostic queries. See [the F6 snapshot format](protocol.md#master-receive-snapshot-f6).

## Earlier receive loss and the RX128-only revision

A later native typing observation recorded two additional frame failures and three exchange timeouts despite the earlier clean three-minute run. Single-owner raw HID tests reproduced missing DATA/COMMIT requests without L-Connect or the native worker. An additional 500 ms of read-only observation found no late acknowledgement. F4 showed that the master received the failing request and submitted its complete 46-byte envelope to the UART FIFO; FIFO submission does not prove physical arrival.

The PLC's real, frozen F5 snapshot then captured a 72-byte DMA-full callback with CNDTR zero, followed by a 47-byte callback. A complete next DATA envelope was visible to the prefix scanner but was not decoded; the parser discarded its 39-byte tail. The previous batch left a nine-byte legacy fragment. Software FIFO push failures were zero. These observations strongly support this sequence: the saturated DMA batch lost seven legacy bytes, allowing the unfinished 17-byte legacy record to consume seven bytes of the next RGB header. Raw key payloads were not recorded, and the exact MCU identity or interpretation of a particular status bit is not claimed.

The correction adds an aligned, owned 128-byte RX DMA array at `0x2000f718..0x2000f798`. Both RX buffer references and all four RX count/remaining-count/reload instructions are updated against exact original byte guards. TX DMA count, TX buffer and UART timing remain unchanged. Initializing compatibility state preserves the already-live RX array. A target regression feeds an 80-byte legacy/RGB/legacy burst and checks both legacy records and the real DATA acknowledgement. Full-buffer and invalid-size boundaries are also tested. The change does not extend the lease, raise reply timeouts or hide failed frames.

On 2026-11-12, the approved PLC image was transferred once through the normal configurator transport. A fresh hardware diagnostic observed callback length 46 plus remaining DMA count 82, confirming a capacity of 128. A subsequent 60-second raw run completed 1,286 frames and 19,300 exchanges without retries, failures or foreign reports; maximum observed reply time was 16 ms. Its complete F5 snapshot recorded zero DMA-full callbacks, zero software push failures, zero parser-discard bytes and a successful final 104-output COMMIT. Natural one-second lease expiry also passed. This bounded run does not establish unlimited stability or native typing acceptance by itself. A subsequent 180-sample native observation completed 4,145 additional frames but recorded three DATA timeouts and recoveries; ten cumulative failures were already present before observation began. Although the user initially reported continued visual Wave output, these counters showed that the RX128-only revision still had transport loss. A second coupled native/PLC run recorded one more DATA timeout while completing 4,258 additional frames; its aggregate PLC counters were zero for DMA-full, push failures and parser discards. Capture windows include startup and shutdown latency, so these aggregates do not localize that individual failure.

A zero-gap raw run then reproduced a failure after 1,600 frames and 24,011 successful exchanges. F4 confirmed DATA transaction 71/index 24 was received by the master and all 46 bytes were submitted to its FIFO; it was still waiting for a PLC reply. F3 showed staging transaction 71, active transaction 70 and missing outputs 24..103. PLC receive metadata captured a full 128-byte DMA batch (CNDTR zero), successful DATA/index 16 decode, then a 47-byte callback containing a complete DATA/index 24 prefix that was never decoded; the parser discarded 44 bytes. The preceding legacy remainder was 14 bytes. This is consistent with another saturated continuous burst truncating a 17-byte legacy record, allowing it to consume the next extension header. Increasing buffer capacity alone is insufficient.

The last snapshot is explicitly partial: 129 of 132 nonce-validated pages, including the complete header and 62 complete records, were retained. Those records include the incident; the final three pages were interrupted by the private host wrapper handling stderr as a terminating error. Missing pages were not reconstructed. The wrapper was corrected separately and the existing runtime/settings were restored. These RX128-only results motivated the circular receive correction described below; they are historical evidence, not the current acceptance result.

## Master FIFO receive correction

The F6 capture later identified a 43-byte buffer matching the prefix of the expected 46-byte DATA acknowledgement. The hardware FIFO and original accumulator were empty, while cached line status was `0x63` with two raw bit-1 events. The PLC had decoded that exact request and called its 46-byte reply sender. These observations strongly support master receive overrun; they do not timestamp each status event, identify the exact silicon, measure physical PLC transmission or identify the missing positions in repeated zero symbols.

The original receive-ready ISR reads exactly seven bytes without checking available FIFO data. The correction lowers the reference trigger to two and reads only while RFC is greater than one, with at most eight reads per interrupt. It retains one byte for the original character-timeout ISR, which drains the final byte and invokes the original receive callback. The WCH reference requires a nonempty RX FIFO before the four-character timeout can occur. See [the WCH CH585/CH584 data sheet, PDF page 79](https://cdn.promelec.ru/upload/grab/datasheet.lcsc.com/lcsc/2512031622_WCH-CH584M_C42381470.pdf).

An earlier trigger-one candidate emptied the FIFO and booted normally but did not deliver PLC replies; it was rejected on hardware and the known working diagnostic image was restored. The revised regression models that missing timeout gate, retains 45 acknowledgement bytes plus one FIFO byte, then validates exact acknowledgement publication after the timeout callback. The revised image passed its initial real VIA/version/calibration/PLC-readiness queries. A bounded seven-minute actual L-Connect run then completed 8,067 additional frames with zero exchange failures, frame failures or recovery attempts. The operator confirmed key input, the display, option changes and Wave output after a short idle interval. After restoration of the original native executable and all thirteen profiles, the operator also confirmed existing RAM/GPU/GC575 lighting, the 8.8-inch screen and updating sensor values, with no repeated return to the stock effect. The automated startup-log sensor check remained inconclusive and was recorded separately from this physical confirmation. Hours-long idle and reuse were not tested.

Both constructor edits have exact original-byte guards: initial FCR `0x87` becomes `0x47`, and the final OR-immediate changes from `0xc0` to `0x40`. The original buffer and 16-bit accumulator are reused, and the timeout ISR, callback, baud, lease and reply deadline are retained. Original RX-buffer capacity and bounds, maximum heap/stack use, effective 8K throughput and prolonged physical IRQ behavior remain unestablished.

## Master binding

The original RawHID entry is at RAM `0x200046ee`. Incoming `a0` is opaque, `a1` carries the endpoint and `a2` the received count. The report lives at static RAM `0x200104c0`. IN-completion callbacks carry bit `0x80` and must pass through without reprocessing a stale OUT report.

IN transmission uses `0x2000355e`, whose DMA retains the caller buffer. The target uses a persistent four-byte-aligned stage until the endpoint remaining-count field clears on completion. OUT rearming is a separate helper at `0x20003736`; a consumed D2 request is copied before the static OUT buffer is rearmed. The earlier identification of this OUT helper as a transmitter was corrected.

The task hook pumps deferred traffic and preserves the original worker's entry registers. D1 updater requests cancel the extension generation and return to the stock handler. UART FIFO writes must check cancellation between bytes. Critical sections mirror the stock CSR `0x800` mask `0x88` save/restore pattern; its hardware meaning and behavior remain device-unverified.

## Owned state and code storage

The current master persistent state is 764 bytes at `0x20012a10`, ending at `0x20012d0c`. Its 4-byte-aligned RAM code starts after the aligned reservation at `0x20012d10` and runs through `0x200144b0` (exclusive end); the coordinated BSS/heap floor is `0x200144b0`. Startup moves the related heap/BSS values together while preserving the original stack guard and stack top `0x20020000`.

The master reuses its original second code-copy source span, flash `0x8214..0x14e04` (52,208 bytes). The current patched suffix packs to 41,686 bytes; the same owned span holds 6,048 bytes of RAM code and 340 bytes of restore helpers, leaving 4,132 bytes after alignment. The original first 528-byte boot copy and clock setup remain intact. A 44-byte copy slot calls the bounded decoder and resumes the original startup sequence. After BSS clearing, the helper copies the new code into reserved RAM and continues with the original initialized-data copy, whose heap-break word is updated. [The RAM-copy manifest](../firmware/targets/dp104-master-ramcopy.json) pins the stock source ranges and hashes.

The current PLC state is 11,244 bytes at `0x2000cbb0`, ending before aligned heap floor `0x2000f7a0`; the initial stack top remains `0x20038000`. The stock PLC allocator exposes no visible upper bound, so the reserved floor and measured image fit do not establish maximum physical heap/stack demand or exclude every indirect alias.

The PLC contains two 8,192-byte arrays matching the pinned official CMSIS4 tables byte-for-byte. It reconstructs the original A table from B by word permutation and sign-bit operations, with one signed-zero correction. The reconstructed table is placed at `0x2000cd1c` after BSS clear and before the original application entry, through the existing descriptor. Source provenance is pinned in [the table manifest](../firmware/targets/dp104-plc-twiddle.json). The current circular-RX PLC payload is 8,128 bytes in the original A-table span at `0x0801cc5c`, leaving 64 bytes in that 8KB span; B and initialized data remain unchanged.

Both payload builders check target ABI, fit, allowed byte changes, preserved data and branch targets. The master review also runs a full packed-bundle CPU harness and independent emitted-byte checks, including all three heap values and decoded AUIPC/ADDI references. The current combined build passed 24/24 CTest cases; portable RV32IMC/ILP32 and Thumb Cortex-M3 soft-float harnesses exited successfully. These checks do not execute the complete firmware, target MMIO or real-time 8K polling. Flash readback, maximum heap/stack demand and independent PLC recovery remain unverified.

## Color order and OpenRGB

The native detector requires a strict live end-to-end CAPS reply before registration. It is source for a native OpenRGB build, not an automatically loaded plugin. It exposes 104 outputs in source index order. The verified coordinate table links the original renderer's 104 slots to key positions, with VIA labels and physical ESC, Space and Enter anchors checked. In L-Connect compatibility mode, each physical LED selects a sample from the incoming linear frame using `sourceIndex = (x * 103 + 112) / 224`; normal keyboard mode keeps identity index order. SDK updates only enqueue the latest frame; a separate worker serializes HID traffic and coalesces pending updates, so a slow keyboard does not block updates to other controllers. Accepted static frames refresh every 250 ms. Transient errors enter bounded CAPS/latest-frame recovery; persistent failures stop updates. Shutdown joins the worker before releasing the device.

The PLC refuses ready CAPS until an operator verifies RGB channel order. Explicit raw-channel pulses expire after one second. Confirmation checks the echoed order and a fresh 16-byte nonce to reject stale acknowledgements. On the tested keyboard, the confirmed volatile permutation is `[1, 0, 2]` (GRB storage) and is reapplied from `DP104Settings` before CAPS. `tools/calibrate.py` prepares calibration commands and prints a settings fragment; it does not edit installed configuration. The table and three anchors support the current X projection, and the user confirmed the projected Wave and L-Connect option changes on the tested keyboard.

The tested L-Connect build omitted the controller when it was exposed as an OpenRGB keyboard, although raw SDK discovery correctly returned eight devices and DP104 version 1.2.1. The explicit `DP104Settings.lConnectCompatibility` option selects the same GPU lighting classification used by the existing GC575 integration. This is a presentation compatibility choice for the real 104-output device; it does not bypass the PLC gate, emulate a successful receiver, modify a vendor DLL or replace the physical key map. Without the option, the controller keeps its normal keyboard classification.

L-Connect assigns ordinary controllers their raw SDK indices, but expands motherboard zones into additional sequential IDs. A GPU-compatible DP104 after a five-zone motherboard therefore collides with an existing zone ID. The combined server sorts GC575 first, then places compatibility-mode DP104 before the motherboard without changing other devices' relative order. On the tested topology this means RAM 0..3, RTX 4, GC575 5, DP104 6 and motherboard 7, with motherboard zone IDs 7..11.

For this topology, motherboard profile IDs 6..10 were migrated once to 7..11, preserving their individual settings and aggregate selections, directions and color temperatures. DP104 uses ID 6 and the current global effect. Numeric IDs can change when devices are absent or the topology changes; this vendor SDK does not provide stable hardware identifiers. The migration is stateful and should not be repeated for a routine firmware or native build update.

## Verification and recovery boundary

The current integrated source passed 24/24 CTest cases. Portable RV32IMC/ILP32 and Thumb Cortex-M3 soft-float QEMU harnesses exited successfully. The master packed-bundle CPU harness and independent emitted-byte review passed, including the three relocated heap references. These checks do not execute the complete device firmware or its MMIO.

The initial 35-second L-Connect trace recorded 934 callbacks, 12,171 HID exchanges, 812 frames started and 811 COMMITs completed, with no reported failures and one frame still in flight at capture end. A subsequent trace on the same process and controller recorded 108 callbacks but zero HID exchanges and zero frame submissions; the worker had stopped. The user then reported that built-in lighting returned and other devices remained normal. The later stop means the initial trace does not establish continued host operation. Fixed-wire physical regression also covered fast varied frames and zero-heavy slow/bare-marker inputs. Earlier escaped-wire trials were different: an immediate F3 snapshot after a timeout showed DATA indices 40..103 missing from the PLC receiver. The exact loss point in the UART path was not identified; the fixed-length format passed the same regression conditions without a missing DATA report. These are bounded observations, not proof of a general root cause or unlimited stability.

The user verified ESC recovery enumeration, read its INFO file and restored normal mode. The master is installed by its documented ESC route; the PLC uses the normal configurator HID transfer. Independent recovery of a corrupted PLC application and flash readback remain unverified. The user confirmed continued X-projected Wave operation and L-Connect color, brightness, speed and direction changes. The user also confirmed that keyboard input, upper display, RAM/GPU/GC575 lighting and the screen/sensors remain normal. Maximum heap/stack headroom and real-time 8K behavior are not established by builds, QEMU or the bounded hardware runs.

## PLC circular receive drain

The accepted PLC implementation keeps 128-byte RX storage and makes it circular. It enables half/full transfer events so the first 64 bytes can be consumed before the array fills. DMA events and USART IDLE share one cursor; only newly received spans enter the existing FIFO/parser. A wrap emits the tail before the head. Repeated boundary observations do not duplicate bytes, and ambiguous laps are explicitly rejected and recorded. No failed frame is acknowledged or replayed by this cursor.

The implementation redirects the default channel-6 vector at `0x08008080` and replaces the existing USART ISR entry at `0x08017564`. It enables IRQ16 with the original USART IRQ38 priority. Exact original-image guards and the [DMA contract](../firmware/targets/dp104-plc-dma.json) pin the register layout. These addresses and the vendor reset-helper channel calculation match the referenced official Artery definitions; the exact fitted MCU remains unidentified. TX configuration, clocks, baud rate, master image, direct lease and host timeout were unchanged by the PLC correction. The separate master correction is described above.

Startup relies on the measured BSS clear before peripherals and preserves live RX storage, cursor and partially received stream. It does not bulk-clear that reservation again after receive activity begins; the coefficient array is rebuilt before application entry. The synthetic target test preserves two RGB requests and all five legacy records in a continuous 177-byte sequence that crosses the old saturation boundary. The standalone cursor also tests wrap, IDLE/HT/TC overlap, duplicate boundary observations and conservative overrun rejection. These are source/host-test results, not proof of real interrupt latency, physical RX operation or complete firmware behavior. The circular receive revision passed 22 host tests and the real target/receiver integration test compiled as ARM Thumb soft-float with synthetic MMIO under QEMU; the current combined source passes 24 tests. The linked payload is 8,128 bytes, leaving 64 bytes in the original 8KB span; the state is 11,244 bytes and its aligned heap boundary remains unchanged. Emitted instructions preserve the USART enable/status gates and one adjacent SR/DR clear pair. These checks do not execute the physical DMA/NVIC or prove real interrupt latency. This PLC image is installed on the tested unit and was used with the corrected master in the seven-minute real L-Connect acceptance run described above.
